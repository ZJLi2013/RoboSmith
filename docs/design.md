# RoboSmith 设计

在真实场景的仿真孪生里评测 agentic 机器人与 VLA。三块：**场景**（真实视频变成可交互孪生）、**操作**（自带的基本 agentic 操作证明任务可解）、
**评测**（被测方跑任务，判定并归因失败）。

## 问题

代码是从数据生成流水线演化来的，目标是「让演示成功」，所以每一层都在**放过不成立的东西**：放不下的物体被跳过、规划不出的动作被硬推、
失败照样判成功。上游放过的问题到下游变成别的症状，原因因此分不清。缺的不是某个组件，而是每层都没有「不成立就失败」的契约。

## 设计原则

- **一套几何**：放置、检查、规划、判定都用仿真里的同一份几何。
- **不成立就失败**：每层带原因失败，不跳过、不降级。

## 三块与进度

| 块 | 要保证什么 | 现在 |
|---|---|---|
| 场景 | 一个场景成立 = 几何一致、物体静止、可动物体能被抓起；每次实例化都自动检查 | 资产与场景求解已有；世界检查未实现 |
| 操作 | 一个动作能执行 = 执行前已在仿真几何里验证可行；所有动作经同一道门 | 已实现：六动作组合、执行门、关节空间规划器；公开验收场景 dev 全部 certified；冻结后读一次留出族 F5，test seed 100–109 为 10/10 |
| 评测 | 被测方经不绑框架的接口接入；报告给出 never / lost 归因 | 只有判定；接口、归因与报告未实现 |

顺序：场景检查与操作先行（评测依赖它们），然后评测接口与报告，最后真实视频导入。数据生成时代的图像转 3D 后端、网格转 URDF、
只被它们调用的资产命名目录（`assets/catalog.py`）与训练脚本已删除；资产生产只剩 agent 写的 Blender 程序与 AHa-3D 快照导入，
不被 import、按路径或名字运行的模块：Blender 脚本（`blender/render.py`、`aha3d/export_roots.py`）、评审校准用例的 build 文件、
`python -m robotsmith.assets.fetch`，以及评审 agent 按 `REVIEW.md` 运行的 `assets/review/probe.py`。还留着的是录制：scenario 运行时每个控制步写 LeRobot 数据集（见评测一节的问题）。

## 场景：真实场景变成可交互的孪生

真实视频导入的场景过了「几何一致、物体静止、可动物体能被抓起」三条才算孪生；agent 写的场景同样。

现在有什么：

- **资产**：agent 写 Blender 程序生成单个物体（含铰接件）；独立 LLM 评审自己写仿真探针取证后准入；准入资产按内容 hash 发布到
  Hugging Face，新 clone 可完整复现；查重分两层（hash 拦精确重复，近似候选交 LLM 判）。
- **场景**：agent 写 YAML（物体、关系、对执行方隐藏的成功树、seed），求解器按 seed 摆放，加载进 Genesis，沉降后检查是否静止。
- **真实场景导入**：视频经外部重建（AHa-3D）→ agent 建房间 → 按快照导入，物体各自编成资产。只在 BEHAVIOR 仿真视频上跑过
  （几何残差中位数 6.2 cm），真实视频没跑过。

三条都还没有被强制：

- **几何不一致**：同一个物体在生成、摆放、评审探针、判定里用的是不同的几何近似（盒子、网格、包围盒）。
- **静止只在部分时机检查**，建场景时不查；放不下的物体被跳过，场景照样加载。
- **没有人检查可动物体能不能抓起**；可抓只在运行任务时才暴露（例：骰子被摆在立柱旁，俯视抓取压进立柱）。
- 桌子在场景文件里是一个资产名，仿真里其实是程序生成的盒子。
- 导入的场景过不了静止检查：导入时能静止，后来物体被顶开约 0.1 m，中间有回归、原因未查。

设计：

- 一套几何：资产只用一种碰撞表示，摆放、检查、判定都读仿真里的同一份。
- **世界检查**：场景每次实例化都自动做——几何一致、静止、每个可动物体经操作层的执行门能抓起；不过即场景无效，结果反馈给写场景的
  agent 返工。
- 摆放 fail-closed：任一物体放不下，场景无效。真实视频导入的产物必须过世界检查才算孪生。

已定 / 不做：资产只走 agentic 生成（agent 写程序或操作工具），不用图像 / 文本转 3D 模型、不用前馈场景模型（网格不透明，无零件与关节）；
资产即物理尺寸，不在场景里缩放；场景求解器只管摆放与可静止，不判任务可解（由操作层证明）。

下一步：世界检查的设计；查清导入场景的静止回归；用一段真实桌面视频（手机绕桌 10–30 s，3–5 件可移动物体）先验证尺度与重力方向。

## 操作：基本 agentic 操作证明任务可解

agent 写步骤表或 plan 文件给出六动作组合，技能执行，每步判定。任务判定成立，且实际执行的每个动作都事先在仿真几何里验证过，
才算证明可解；不可行就带原因零步失败。设计见 [manipulation](manipulation.md)，代码路径见 [call-chain](call-chain.md)，
验收见 [acceptance](acceptance.md)。

## 评测：被测方跑任务，判定并归因失败

被测方（agentic 系统或 VLA）经一个不绑框架的接口跑任务；判定读仿真状态、对照被测方看不到的成功树；每个失败说出哪个里程碑
**从未达到**（never）或**得而复失**（lost）。MVP 报告样例：

```text
RoboSmith eval  scene: <your desk>  evaluatee: <agentic baseline>
task                          certified  success  failures
put the cup on the tray       10/10      6/10     never: grasped ×3 · lost: on ×1
```

结论只在孪生里成立；没做过孪生与真机的对照，不作真机结论。

现在有什么：判定的谓词读仿真状态，任务与每一步共用，判定所用的状态整份保存、可离线复判，失败列出没成立的条件；两种角色：
证明可解（看得到成功树）与基线被测方（看不到）。

问题：

- 没有被测方接口：只能跑 RoboSmith 自己的技能。
- 运行时绑着数据录制（每个控制步写数据集），输出状态还叫「数据生成成功 / 失败」。
- 只有「哪些条件没成立」，没有 never / lost 归因，没有报告。
- 渲染在 MI300X 上是 CPU 光栅：Genesis 物理在 GPU，渲染经光栅器落到 Mesa llvmpipe，约 28 s / episode
  （320 px 比 640 px 快 2–4×），没有光追，还不适合 VLA。Instinct（CDNA）没有光追硬件，
  [HIP RT](https://github.com/GPUOpen-LibrariesAndSDKs/HIPRT) 在其上只能软件遍历；Genesis 光追器未在 MI300X 上试过。
  一个进程只能跑一个场景。

设计：

- 录制改为可选的观察者，不在执行循环里。
- 接口第一版只接技能级：被测方给步骤，RoboSmith 经操作层的执行门执行；第一个被测方就是自带的基线 agent。之后再接动作级（VLA）。
- 归因：成功树的叶子按顺序当里程碑；按时间线判 never（从未成立）或 lost（成立过、终态丢失），先用合成状态序列钉住各种情形。
- 报告：按场景、任务、被测方汇总 certified / success / never / lost。

已定 / 不做：接口不绑任何框架（vla-eval、RPent 都只是适配目标）；记忆、感知、VLA 需要时接外部框架（如 RPent）；
不做标准 benchmark 套件、不训练策略、不做 sim-to-real 研究。

开工前提（操作层冻结并读完留出族）已满足；提前探 MI300X 上 Genesis 能否 GPU 渲染。
